# HANDOFF: переработка бенчмарка в честное сравнение языков

Документ передаёт контекст обсуждения новой сессии или другому ассистенту, чтобы продолжить работу на локальном ПК.
Код по новому плану **ещё не написан**: согласованы цели и правила, тулчейны были проверены в облачном контейнере.

---

## 1. Исходное состояние репозитория

- `src/c/main.c`, `src/cpp/main.cpp`, `src/csharp/Program.cs`: сумма 200 млн `int32` (800 МБ) на ручных AVX2-интринсиках
  (4 аккумулятора, выровненные загрузки), 50 итераций, печать времени каждой итерации. C# использует `unsafe` и `NativeMemory`.
- `run_benchmarks.ps1` запускает C# (`dotnet run`), затем C и C++ (`gcc/g++ -O3 -mavx2`).
- `README.md`: таблица «Best Time», где C# первый (23,40 мс), C++ 23,89 мс, C 24,20 мс.

**Система автора:** Intel Core Ultra 9 285K, 2×32 ГБ Kingston Fury DDR5-6000 (dual channel), Windows (судя по `.ps1`/`.exe`),
GCC/G++ 14.2.0, .NET 10.

## 2. Итоги разбора честности старого бенчмарка

1. Бенчмарк ограничен памятью, а не кодом. 800 МБ за ~23 мс дают ≈34 ГБ/с, это ≈35 % от теоретических ≈96 ГБ/с
   DDR5-6000 dual channel. Это потолок **одного потока** (буферы заполнения линий кэша и задержка памяти),
   а не потолок DRAM. Разница 1–3 % между языками находится в пределах шума.
2. Метрика «Best Time» (минимум из 50) не показывает разброса. Нужны медиана, stddev, min и max.
3. Порядок запуска фиксирован (C# первым), раунды не чередуются.
4. Код с интринсиками одинаков во всех языках, поэтому сравнивается кодогенерация одних и тех же интринсиков,
   а не языки. Такое сравнение малоинформативно.

**Решение автора:** отказаться от этого типа бенчмарка и **удалить** AVX2-версии полностью, без папки `micro/`.

## 3. Общая цель

Честное сравнение **идиоматичных решений практических задач** на C, C++, C#, Rust и Go.
Вопрос, на который отвечает бенчмарк: «что получит разработчик, написав задачу обычным для языка способом,
и сколько выиграет, если оптимизирует её в рамках тех же правил».
Сравниваются **языки вместе с их стандартными библиотеками и рантаймами** (GC, JIT, AOT), и это прямо
говорится в README.

## 4. Согласованные правила (подтверждены автором)

| Пункт | Решение |
|---|---|
| C | **C23** (`-std=c23`), только libc (кроме JSON) |
| C++ | **C++23** (`-std=c++23`), только стандартная библиотека (кроме JSON), без raw `new` |
| C# | .NET 10, только BCL, **без `unsafe`**. `Span<T>`, LINQ, `Vector<T>`, `MemoryMarshal` допустимы |
| Флаги C/C++ | **Только `-O3 -march=native`** (других режимов нет) |
| .NET | **`dotnet publish -c Release`**, а не `dotnet run`. Две отдельные строки в таблице: **JIT** и **NativeAOT** |
| Уровни реализации | **A**: простой идиоматичный код «как пишут в первый раз». **B**: оптимизированный, но в тех же правилах |
| Корректность | У каждой задачи есть эталонный вывод. Если реализация не проходит проверку, её **исправляют**, а не исключают |
| Замер | Весь процесс (wall time, CPU time, пиковая память) плюс steady-state внутри процесса. Медиана и stddev, чередующийся порядок запусков |
| JSON | Входит в набор задач. Источник интереса — source generator `System.Text.Json` |
| JSON-библиотеки | Матрица A/B (см. ниже) через CMake `FetchContent` с зафиксированными версиями |
| Старый код | Удалить |
| Новые языки | **Добавить Rust и Go** (решение автора; детали правил ниже — пока только предложение) |

### JSON-матрица

| Уровень | C | C++ | C# | Rust* | Go* |
|---|---|---|---|---|---|
| A (самое популярное) | cJSON | nlohmann/json | `System.Text.Json` с рефлексией (**только JIT**: в AOT рефлексия не работает) | serde_json | `encoding/json` |
| B (быстрое идиоматичное) | yyjson | glaze | `System.Text.Json` **source generator** (JIT и AOT) | sonic-rs или simd-json | easyjson (кодогенерация, аналог source gen) или `encoding/json/v2` |

## 5. Важные технические нюансы (не потерять)

- **NativeAOT по умолчанию собирается под базовый x86-64-v2**, без AVX2. Для паритета с `-march=native` в AOT-профиле нужно
  указать `<IlcInstructionSet>native</IlcInstructionSet>`. JIT и так использует все инструкции процессора.
- **Аналоги `-march=native`** (предложение): Rust `RUSTFLAGS="-C target-cpu=native"` с `--release`;
  Go `GOAMD64=v3` (у 285K нет AVX-512, поэтому v3 — максимум). Go не векторизует автоматически, это свойство языка, и его нужно указать в README.
- **FMA-контракция:** при `-march=native` GCC в ISO-режимах (`-std=c23`/`c++23`) по умолчанию использует `-ffp-contract=off`,
  а в GNU-режимах `fast`. Стоит проверить и зафиксировать явно, иначе результаты с плавающей точкой будут расходиться между языками.
- **JIT-прогрев:** время всего процесса включает запуск и JIT. Поэтому нужны оба режима, «холодный» (1 повтор) и «тёплый» (N повторов).
- **Общий генератор данных во всех языках**, чтобы входы были идентичны. Предлагается SplitMix64:
  ```
  state += 0x9E3779B97F4A7C15
  z = state
  z = (z ^ (z >> 30)) * 0xBF58476D1CE4E5B9
  z = (z ^ (z >> 27)) * 0x94D049BB133111EB
  return z ^ (z >> 31)          // всё по модулю 2^64 (wrapping)
  ```
- **Проверка вывода:** сравнивать токены с эталоном, числа с плавающей точкой с допуском около 1e-7 (относительным или абсолютным).

## 6. Предлагаемый набор задач (черновик, детали обсуждаемы)

| Задача | Что проверяет | Заметки по честности |
|---|---|---|
| **binary-trees** (как в Benchmarks Game, depth ~21) | Аллокации, GC против malloc/new | Rust: `Box`; Go: GC; C#: классы |
| **word-freq** (текст ~100 МБ, топ-20 слов) | I/O, строки, хеш-таблица | Вход генерируется детерминированно. Сортировка: count desc, затем word asc |
| **sort** (10 млн записей `{key u64, id u32}`) | Стандартная сортировка | A: `qsort` / `std::sort` / LINQ `OrderBy` / `sort_unstable_by` / `slices.SortFunc`. B: одинаковый LSD radix sort в безопасном коде (видна цена проверок границ) |
| **n-body** (5 тел, как в Benchmarks Game) | Скалярные вычисления на `double` | Вывод `%.9f`, проверка с допуском |
| **matmul** (1024×1024 `double`) | Циклы и доступ к памяти | Элементы — маленькие целые числа, тогда сумма **точна** при любом порядке и проверка строгая. A: наивный ijk (в C# `double[,]`). B: ikj и блокировка; в C# `Vector<T>`, потому что JIT не автовекторизует |
| **array-sum** (переосмысление старого кода) | Автовекторизация | A: цикл, `std::accumulate`, LINQ `Sum`, `iter().sum()`, `for range`. Данные случайные из [-1000, 1000], результат `int64` |
| **json** (массив ~500k объектов: id, name, email, active, score, tags[], address{city,zip}) | Разбор в типизированные структуры и сериализация | Вывод: count, active count, сумма score (у score два знака после запятой, так что разбор однозначен). Размер сериализованного JSON печатать в stderr без проверки: форматирование `double` у библиотек разное |

## 7. Предлагаемая структура репозитория (черновик)

```
RULES.md                      # правила языков (раздел 4), обязательный документ
README.md                     # система, методика, таблицы (медиана ± stddev)
tasks/<task>/SPEC.md          # формальная спецификация, размеры, формат вывода
tasks/<task>/expected.txt     # эталонный вывод
tasks/<task>/{c,cpp,csharp,rust,go}/{a,b}/...
c/CMakeLists.txt, cpp/...     # glob по tasks/*/c/*, FetchContent для JSON
csharp/Directory.Build.props  # общие настройки publish, профили JIT/AOT, IlcInstructionSet=native
tools/                        # генератор данных и раннер
```
- Каждая реализация — **отдельный исполняемый файл**. Вход: `<input|size> [repeat]`. Результат пишется в stdout,
  время каждого повтора в stderr (`iter_ms <value>`).
- Раннер (PowerShell 7 или C#) собирает всё, запускает в чередующемся порядке, сверяет вывод с `expected.txt`,
  считает медиану, stddev, min, max и пиковую память (`Process.PeakWorkingSet64`) и генерирует таблицу для README.

1. Подтвердить у автора правила для Rust и Go и колонки JSON-матрицы для них (раздел 4).
2. Подтвердить или скорректировать набор задач и размеры (раздел 6).
3. Удалить `src/` (AVX2-версии) и старую таблицу в README.
4. Написать `RULES.md` и `tasks/*/SPEC.md`.
5. Сделать инфраструктуру: CMake (C23/C++23, `-O3 -march=native`, FetchContent), `Directory.Build.props` (JIT/AOT, `IlcInstructionSet=native`),
   Cargo workspace, Go module, генератор данных, раннер с проверкой и статистикой.
6. Реализовать задачи (A и B) на 5 языках. Начать с одной задачи сквозным образом (например, n-body), проверить раннер, затем остальные.
7. Прогнать на 285K и заполнить README: система, методика, таблицы.
